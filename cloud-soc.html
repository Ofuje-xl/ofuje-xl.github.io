# Overview

I built the foundation for a Microsoft-focused cloud SOC using Azure, Microsoft Sentinel and a Windows 11 endpoint. Rather than treating the project as a portal walkthrough, I designed the environment around practical security constraints: least exposure, predictable cost, clear network segmentation and reusable infrastructure for later detection work.

The completed foundation will be used in later phases to ingest Windows telemetry, write KQL hunting queries, create analytics rules, investigate incidents and add automation.

# Security & Cost Decisions

  • Used Azure for Students and configured a monthly budget with cost alerts.
  • Kept Sentinel and Log Analytics in an allowed region supported by the student subscription.
  • Used a low-cost B-series Windows VM instead of higher-cost D/F-series compute.
  • Enabled Trusted Launch, Secure Boot and vTPM on the Windows endpoint.
  • Used a Standard SSD and avoided unnecessary data disks, Ultra Disk and capacity reservations.
  • Did not expose RDP broadly to the internet.
  • When direct RDP was required, the temporary rule was restricted to a single source IP.
  • Kept paid Bastion disabled because the free Developer SKU was unavailable in the endpoint region.
  • Validated outbound HTTPS connectivity before moving to telemetry onboarding.

# RBAC & Identity Lesson

A useful design constraint appeared early: the Azure for Students subscription was associated with a university-managed Microsoft Entra tenant. I had Owner rights over the Azure subscription, but that did not make me a Security Administrator or Global Administrator in the Entra tenant.

Key lesson: Azure RBAC controls access to Azure resources such as VMs, VNets and Log Analytics. Microsoft Entra roles control directory-level objects and tenant administration. Subscription Owner does not automatically imply tenant administrator.

Because of this separation, Sentinel-to-Defender portal onboarding was deferred rather than trying to modify a tenant I do not administer.

# Challenges & Troubleshooting

01 — Region policy restriction

Problem: The student subscription blocked the original UK South deployment.

Resolution: Reviewed the allowed-region policy and deployed the Sentinel workspace in Switzerland North.

02 — VM SKU unavailable

Problem: Suitable Windows 11 VM sizes were unavailable in Switzerland North for the subscription.

Resolution: Kept Sentinel in Switzerland North and moved the endpoint workload to Poland Central, where Standard_B2als_v2 was available.

03 — Bastion cost constraint

Problem: Bastion Developer was not available in Poland Central, while paid Bastion introduced an hourly cost.

Resolution: Used a temporary public IP with an NSG rule allowing RDP only from the current trusted source IP, with cleanup planned after each working session.

04 — VM Agent not ready

Problem: The Azure VM Agent initially reported as not ready.

Resolution: Verified boot health and rechecked the agent state; the endpoint later reported Ready without rebuilding the VM.

# Verification

From the Windows endpoint, I verified the expected private addressing and outbound connectivity. The endpoint received 10.20.10.4/24 with gateway 10.20.10.1, and HTTPS connectivity to Microsoft services succeeded.

Phase 1 outcome: Azure infrastructure, Sentinel, Log Analytics, RBAC fundamentals, endpoint networking and the Windows endpoint are all operational. The environment is ready for telemetry ingestion and KQL work.

# Reflection

The most valuable part of this phase was learning how cloud security decisions interact with real platform constraints. Region policy, subscription limits, identity boundaries and recurring service costs affected the design as much as the technical requirements.

I also reinforced an important operational principle: secure cloud architecture is not simply about enabling more security products. It is about understanding trust boundaries, reducing unnecessary exposure, controlling cost and validating that each component behaves as expected before adding complexity.

# Next Phase

Phase 2 will connect Windows security telemetry to Microsoft Sentinel and use KQL to investigate real activity generated inside the endpoint. The next milestone is to move from infrastructure deployment into detection and hunting.
